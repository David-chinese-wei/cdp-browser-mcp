## browser-devtools-mcp：公网站点核对 + network_body 乱码修复（同一天续做）

用户要求用公网站点实测，核对 MCP 提取内容与 `site/` 目录一致，有问题就修。新增 `scripts/verify-site.mjs`（A 层页面内 fetch 算 SHA-256 + UTF-8 逐字符；B 层 network_list/network_body/page_dom/capture_save 全链路）。

首跑 B 层 13 项失败，定位两类根因：

1. **`network_body` 把无 charset 的 UTF-8 文本解码成乱码（真 bug，已修）**。`site/` 以 `text/plain`、`text/markdown` 提供且**未声明 `charset=utf-8`**。CDP `Network.getResponseBody` 没声明 charset 时退回浏览器区域默认编码：英文系统 Latin-1/CP1252（字节可逆），中文 Windows 上是 **GBK（不可逆改坏字节）**。结果 `sample.txt`/`notes.md` 经 network_body 取回乱码（2113/2315 字符 = 字节数，而非 1310/1416）；`data.json`（`application/json` CDP 强制 UTF-8）正常。`page_evaluate(fetch().text())` 却始终正确——因为 WHATWG Fetch 规范对无 charset 文本默认 UTF-8。
   - 修复 `src/capture/session.ts` 的 `networkBody`/`recoverTextBody`：声明了 charset 信任原文 → 单字节做 Latin-1/CP1252「字节→UTF-8」往返（一致即采用）→ 仍不匹配则经页面 `fetch(url)` 重新拉取原始字节按 UTF-8 解码（只对同域 GET 文本兜底，失败保留原文）。
   - 关键判据：`Buffer.from(s,'latin1')` 与原始字节在首个非 ASCII 字节（如 0x99）就不一致 → 说明 Chromium 用的是 GBK 而非 Latin-1，纯 Latin-1 恢复无效，必须走 fetch 兜底。
2. **verify 脚本断言写错（非 MCP bug）**：「没有失败请求」把 favicon 404 / 页面 `fetch(HEAD)` 预检 / `net::ERR_ABORTED` 良性中止都算失败；B2 用含响应头的 `encodedDataLength` 和 `hits[0]`（可能是 `<audio preload>` 的 190 字节 Range 请求）。已加 `benign()` 过滤、改取同 URL 体积最大条目并允许响应头余量。

验证：verify-site.mjs 对**本地**（python http.server）与**公网**两种来源均 0 失败（`✓ 公网站点内容与本地目录完全一致`）；`npm run smoke` 回归全绿。

### 可复用经验
- 静态资源服务 UTF-8 内容**必须声明 `charset=utf-8`**；`Network.getResponseBody` 的 `base64Encoded:false` ≠ 已正确 UTF-8 解码，中文 Windows（GBK 默认）尤其危险。
- 诊断 CDP 文本乱码：先看 `body` 的 code point 分布 + `Buffer.from(s,'latin1')` 是否与原始字节一致，能区分 Latin-1 误解码 vs GBK 不可逆误解码。

## 14:45 补齐 Sources 面板视角（34 → 36 工具）

用户截图指出「开发者工具 → 源代码 / Sources → 页面」面板里的内容都应能抓取。逐项核对后：

**新增 2 个工具**（`resources_list` / `resources_get`），工具数 34 → 36：
- `src/types.ts` 加 `PageResource` / `ResourceTreeNode` / `ResourceTreeSnapshot`。
- `session.resourceTree()`：CDP `Page.getResourceTree`（`RawResourceFrameNode` → `normalizeResourceFrame`），还原 frame 树并把主 frame 自身 URL 补成 `Document` 资源；每个资源还会用 `networkByUrl()` 交叉带出 `requestId`/`status`/`size`。主 frame 标签固定为 `top`，与面板一致。
- `session.resourceBody(url)`：三级兜底 —— 抓到的网络请求 → **失败则页内 `fetch` 重新拉取**（`fetchResourceInPage`，`arrayBuffer` + `btoa` 取原始字节）。
- `tools/content.ts` 注册，返回体带 `source: 'network' | 'page-fetch'` 便于看清取自哪条路径。

**为什么必须加页内重拉兜底**（实测踩到的三种读不到）：
1. 页面用 `fetch(p,{method:'HEAD'})` 探文件大小 → `data.json`/`notes.md` 只有 HEAD 记录，无 body。
2. `<audio preload>` 发 `Range` 请求 → `audio/sweep.wav` body 不被保留。
3. 体积过大 / 页面已导航 → 浏览器丢弃 body。
这三种情况在真 DevTools 里都能点开看到文件，所以「取不到」属于保真度缺口。

**关键认知（不要记错）**：`data.json` / `notes.md` / `sample.txt` 这类**由 `fetch()` 加载的资源不会出现在 Sources → 页面 树里**——真实 DevTools 也不列。所以覆盖率断言不能拿本地文件硬套资源树，正确的两项断言是：①树里每个资源都能 `resources_get` 读到且与本地一致；②本地每个文件都能读到（走兜底路径）。

**新增脚本** `scripts/verify-sources.mjs`（`npm run verify:sources`），与 `npm run verify:site` 配套。踩坑：`walk()` 递归时对子目录调用 `relative(dir,...)`，`dir` 变成子目录导致只返回 basename，必须把 root 单独传。

## 15:50 Chrome 实测：修掉 2 个真 bug + 一批脚本假失败

结论先说：**Chrome 本身没坏**（153.0.8010.53）。`chrome.exe --version` 会吐 GCM registration / TensorFlow Lite、`length_error` 等无关噪声日志，极易被误判成损坏；实测 `--headless --dump-dom` 正常输出，全流程可用。

**真 bug 1：`decodedBodyLength` 重复累加**
`Network.dataReceived` 每分片触发一次，原代码先 `update({decodedBodyLength: chunk})` 覆盖，再 `+= chunk` → 结果 = 最后一片 × 2。污染 `har.ts` 的 `content.size` 和 `csv.ts` 体积列（实测 sample.txt 记成 4226，真实 2113）。改成纯累加。
- 教训：**CDP 累加类字段务必确认 patch 语义是"覆盖"还是"累加"**，两者混用最难发现。

**真 bug 2：`resources_get` 返回半截内容**
请求未 `loadingFinished` 时 `Network.getResponseBody` 会静默返回已到达部分。Chrome 跑测时 `images/waves.png` 只回 9282 字节（应 63191）——而且是**偶发**的，取决于读取时机，极难复现。
- 修：新增导出 `bodyLooksComplete(result, entry)`，未 finished 或实际字节 < `decodedBodyLength-1` 就转走页内重拉；`network_body` 同步加 `partial` 标记 + hint。
- 注意：`decodedBodyLength` 是**线上字节数**，gzip/br 压缩的资源它天然小于解压后体积，此时会误判不完整 → 退化为页内重拉（仍正确，只是慢一点）。这个保守方向是对的。

**脚本假失败（非 MCP bug）**：`smoke-edge.mjs` 里 `filter:'edge'`、`display==='Microsoft Edge'`、`/edg/i` 三处写死 Edge，加 --target chrome 必挂。已改为按目标浏览器推导 `DISPLAY` / `IDENT`（edge→/edg/i，其他→去掉非字母的 kind）。**通用化脚本时先 grep 写死的品牌名。**

**核对脚本稳定性**：`verify-sources.mjs` 原固定 sleep 6s 就抓资源树，懒加载资源未到位时树只有 1 项，比对形同虚设。改为轮询直到资源树连续两次不变后才开始比对。

**双浏览器全绿**：smoke(chrome/edge)、acceptance(chrome/edge)、verify:site(公网/本地)、verify:sources(chrome/edge) 全部 0 失败。新增 npm：`verify:sources:chrome`。

## 17:xx 多浏览器实测（接"其他主流浏览器，360除外，火狐可以"）

**结论：不是所有浏览器都通过。Chrome/Edge 稳过；Vivaldi 受阻；Firefox 架构不兼容；Opera/Brave 本机装不上。**

**Vivaldi 8.2.4133.76 的关键发现（实测，已证伪旧假设）**：
- 旧假设"缺 `--disable-gpu` 导致 headless 35s 超时"是**错的**。实测：带 `--disable-gpu` 反而让 Vivaldi 连调试端口都起不来（/json/version 40s 超时）；不带则浏览器正常启动。
- **真根因**：Vivaldi 的 `browser-level` CDP 完全正常（`Target.getTargets` 35ms、`createTarget`、`attachToTarget` 秒回），但**所有 session 级命令（`Runtime.enable`/`evaluate`）在 flatten 会话方式下一律 8s 无响应**。
- MCP（`session.ts`）用的是 flatten 会话：`client.attachToTarget` + 命令带顶层 `sessionId`。Chrome/Edge 同方式秒回，只有 Vivaldi 挂起。
- **可行修复路径**：改用 `flatten:false` 的 `Target.attachToTarget`，所有命令经 `Target.sendMessageToTarget` 转发、结果从 `Target.dispatchMessageFromTarget` / `Target.receivedMessageFromTarget` 事件回收。已用 `probe-vivaldi3.mjs` 验证：该路由下 `Runtime.enable` 8ms 返回 OK。但这是会话命令层重构（动 `client.send`/`attachToTarget`/事件分发），需保证 Chrome/Edge 不回归，**未擅自实施**，待用户确认。
- 之前"headless 正常"的误判来源：探针漏把 `sessionId` 放进 CDP 消息，实际只测了 browser-level 命令。

**Firefox 156.0.1**：`/json/version` 返回 404（CDP 已移除，v141+ 起）。WebDriver BiDi 可用（导航/DOM/网络/截图/storage 已验证通过），但 MCP 是 CDP 架构，集成 BiDi 需抽象传输层，工作量较大，本轮未做。Firefox 仅 1 个并发 session。

**Opera / Brave**：本机安装 `exit -1`（权限），未测试。

**360**：按用户要求排除。

**复用经验**：诊断"session 级命令挂起"要真正把 `sessionId` 作为顶层字段带进 CDP 消息（flatten 写法），否则测得的是 browser-level，会误判"正常"。区分 browser-level 与 session-level 是这类 CDP 多浏览器适配的第一道坎。
